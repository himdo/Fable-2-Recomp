# Related repositories, forks and upstream work relevant to the Fable 2 Recomp macOS port

Date: 2026-10-13. Read-only GitHub survey (gh CLI + raw file fetches). Nothing was forked, starred, commented on or pushed.

Our project: `rasty94/Fable-2-Recomp` (branch `macos-port`), SDK fork `rasty94/rexglue-sdk` (branch `macos`, 12 ahead of `himdo/rexglue-sdk` main).
Bottlenecks on M3 Pro (3D scene ~68 ms/frame): MSAA on MoltenVK (~50 ms, 2x costs the same as 4x), tessellation emulation (compute + render-pass restart per draw, now replaced for continuous quad patches), memexport readbacks, point sprites, render pass restarts.

### 1.1 Apple / MoltenVK / Metal forks

**[bigmah/rexglue-sdk](https://github.com/bigmah/rexglue-sdk/tree/macos-arm64-fixes) `macos-arm64-fixes`** — 9 ahead, 0 behind main (2026-08-26..09-04). The most directly applicable work found.
- [`38955c4916`](https://github.com/bigmah/rexglue-sdk/commit/38955c4916) "Cut the render pass churn that stalls tile-based GPUs" (2026-09-04). Measured a loaded save at 21 FPS/720p with the GPU ~90% busy and >240 Vulkan render passes per frame, ~200 of them re-entering the same render target right after it was closed (each one stores+reloads the whole colour and depth buffer on a TBDR GPU). Two cvars:
  - `shared_memory_upload_coalesce_kb` (default 4096): a draw touching CPU-dirtied guest memory must upload it and that upload breaks the open render pass; draws walk a dirtied vertex buffer slice by slice (~20 pass breaks per buffer). Uploads the whole contiguous invalidated run instead (only invalid pages, GPU-written pages stay valid).
  - `vulkan_narrow_render_area` (default on): render targets are allocated for the full EDRAM-addressable height (1280x2048 for a 1280-wide surface) and the render area is what gets stored/loaded; bounds each pass by the guest scissor for draws and by the transfer rectangles for EDRAM ownership transfers.
  - Result over matching 100 s windows, uncapped: 42.1 -> 66.2 FPS, render passes/frame 218 -> 79, attachment area 529 -> 42 Mpx/frame; gain grows with load (1.4x at 1500 draws/frame, 2.0x at 2500). `REX_FRAMELOG=<path>` writes the per-frame CSV.
  - Files: `src/graphics/vulkan/command_processor.cpp` (+117/-13), `src/graphics/command_processor.cpp` (+110), `src/graphics/shared_memory.cpp` (+61), `src/graphics/vulkan/render_target_cache.cpp` (+24/-1), `include/rex/graphics/vulkan/command_processor.h`.

## 2. Other ReXGlue games on macOS or with GPU performance work

### 2.1 andrew17182/Fable-2-Recomp: Fable 2 on a native Metal plugin (XeniOS backend)

[`feature/macos-playtest`](https://github.com/andrew17182/Fable-2-Recomp/tree/feature/macos-playtest) (2026-09-29..10-08). `backends/metal/` adapts **XeniOS's Metal backend** (snapshot `87b176a0`) to the ReXGlue 0.10.0 plugin ABI (`sdk-metal.patch`, 1.25 MB, applied to a private copy of the SDK graphics sources; installed runtime unchanged), with a pinned [xenios-jp/DirectXShaderCompiler](https://github.com/xenios-jp/DirectXShaderCompiler/tree/55db9bc0bc574816d60073872b6a209f7c3d7f0a) fork for `dxbc2dxil` and Apple's Metal Shader Converter (ucode -> DXBC via the existing DXBC translator -> DXIL -> Metal IR; Metal Shader Converter emulates geometry and tessellation stages). Hull shaders ship as DXBC 5.1 bytecode headers (`continuous_quad_4cp_hs.h`, `adaptive_*`, `discrete_*`). macOS 15+, Apple Silicon only, Vulkan kept for Intel. Documentation in `docs/` is extensive (`perf-headroom-20261007.md`, `weak-mac-perf-20261008.md`, `macos-metal.md`, `upstream-rexglue-issues.md`, `bug-patterns.md`, `FPS_CAP_INVESTIGATION.md`).

Measured numbers (M5 Max 40-core GPU, Old Tomb 30 s camera sweep, uncapped): **134 -> 161 FPS, GPU 7.46 -> 6.29 ms/frame mean (p95 10.9)**, cores busy 3.38 -> 1.45 at 60 FPS. Predicted M3 Pro 18-core: 12.5-19.4 ms GPU/frame, "borderline" 52-80 FPS average, heavy views 31-47; 14-core "unlikely" (40-62 avg). Per-change results (each with an env kill switch, commits [`864d4246`](https://github.com/andrew17182/Fable-2-Recomp/commit/864d4246), [`c52ea0a8`](https://github.com/andrew17182/Fable-2-Recomp/commit/c52ea0a8), [`ef356688`](https://github.com/andrew17182/Fable-2-Recomp/commit/ef356688), [`254e3d5f`](https://github.com/andrew17182/Fable-2-Recomp/commit/254e3d5f), [`f0f52f41`](https://github.com/andrew17182/Fable-2-Recomp/commit/f0f52f41), [`dde8114a`](https://github.com/andrew17182/Fable-2-Recomp/commit/dde8114a)):

- `FABLE2_UPLOAD_PRECOMMIT`: staged shared-memory uploads whose pages were last read only by committed command buffers go into one pre-commit blit command buffer per main CB (WAR via GPU-only `MTLEvent`, RAW via fences) instead of ending the open render pass. Staged-upload pass breaks 5.5 -> 0.03 per frame.
- `FABLE2_TEXTURE_PRECOMMIT`: untile/convert texture loads of a draw flush go into the same pre-commit CB when the texture was not sampled in the open CB and its source is not GPU-written there. Main-pass breaks ~9.5 -> ~1 per frame; GPU 6.14 -> 5.9 ms.
- `FABLE2_RENDER_BARRIER_DEDUP`: skip memory barriers / fence waits already covered in the same encoder (~260 barriers + ~1050 fence waits per frame). Uncapped 134 -> ~160 FPS.
- `FABLE2_MEMEXPORT_GEOM_FALLBACK`: the memexport-only vertex shader (VS `695413A9`, computes per-patch tessellation factors for the 336 tessellated terrain draws, VS `5003700B7C9B1C16`) runs export-only (vertex pipeline, no fragment stage, no geometry emulation). Mode 1 cost ~16% uncapped FPS; export-only fixed it.
- Dog-fur flashes: fur shell vertices are memexported; CPU page invalidation re-uploaded stale RAM over them. `FABLE2_MEMEXPORT_PRESERVE` (skip re-upload of recent export ranges with unchanged guest bytes) and `FABLE2_MEMEXPORT_READBACK` (copy export ranges back to guest RAM after CB completion via the unwatched physical view, no GPU wait). 0 flashes vs 3-12 per run.
- `FABLE2_GAME_TICK_SLEEP` / `FABLE2_RING_WAIT`: GameThread and 3D Engine block (kqueue timer / progress event) instead of spinning on the ring read pointer; busy cores at 60 FPS 3.08 -> 1.45. `FABLE2_GPU_CMD_QOS`: GPU Commands thread at user-interactive QoS.
- Opt-in 60 FPS via mid-asm hook at `0x82B9C8E8` (frame-dispatch interval one vblank instead of two); auto 60/30 by IOKit `gpu-core-count` (>= 24 cores).
- Correctness on ARM64: `apply_recomp_patches.py` inserts a host fence after each of the 147 `sync/lwsync` sites that 0.10.0 codegen drops ("rare load crashes and AV storms stopped") — upstream `development` now has "feat(codegen): add sync fences for sync, lwsync, and eieio". `docs/upstream-rexglue-issues.md` also documents `CommandProcessor::InitializeRingBuffer` replaying old ring packets on re-init (Fable II calls `VdInitializeRingBuffer` three times at boot; ~1/200 boots hang) with a park/drain workaround, and `CallInThread` pushing to an unlocked queue.
- The Vulkan path (`docs/macos.md`) carries the tessellation-constants binding fix as `vulkan_tessellation_constants_fix` (default on for macOS) applied by `tools/macos_terrain_fix.py`.
- `perf-headroom-20261007.md` lever list for weaker Macs: "3. An MSAA downgrade option. Draw guest 4x MSAA targets at 2x or 1x on low-end GPUs" — "not a toggle-sized change"; "Not a lever: `metal_fable_terrain_uniform_tessellation=false`" (adaptive tessellation made no measurable difference).

### 2.2 XeniOS (the Metal backend itself)

## 3. Xenia work relevant to the bottlenecks

- **Render target path on Vulkan** (`render_target_path_vulkan` in xenia-canary `vulkan_render_target_cache.cc`): `fbo` = host framebuffers + fixed-function blend/depth, "performance limited primarily by render target layout changes requiring copying, but generally higher"; `fsi` = manual pixel packing in an EDRAM SSBO under fragment shader interlock, "performance limited primarily by overdraw"; **"Any other value: ... currently always FB because the FSI path is much slower now"**. FSI additionally requires `fragmentShaderSampleInterlock|PixelInterlock`, `fragmentStoresAndAtomics`, `sampleRateShading`, `standardSampleLocations`. MoltenVK exposes `VK_EXT_fragment_shader_interlock` (raster order groups) and our SDK links it, but sample-rate shading on Apple GPUs has open bugs (MoltenVK [#2765](https://github.com/KhronosGroup/MoltenVK/issues/2765) `gl_FragCoord.z` not per-sample, [#1656](https://github.com/KhronosGroup/MoltenVK/issues/1656), [#1311](https://github.com/KhronosGroup/MoltenVK/issues/1311) deadlocks). Conclusion: stay on `fbo`; FSI is not a performance path on MoltenVK.
- **2x MSAA**: the Vulkan RTC only uses native 2x if `framebuffer*SampleCounts & sampledImage*SampleCounts` include 2 and `sampledImageIntegerSampleCounts` is not 4-only; otherwise **2x is emulated as samples 0 and 3 of a 4x target** (`msaa_2x_attachments_supported_`; cvar renamed `native_2x_msaa` -> `debug_msaa_2x_as_4x` in canary/stuken). This is the most likely reason "2x and 4x cost the same" for us: check what MoltenVK reports for `sampledImageIntegerSampleCounts` and friends on the M3 Pro (`vulkaninfo`), and whether the SDK's `native_2x_msaa` (default true in `src/graphics/flags.cpp`) actually results in 2x attachments. XeniOS's Metal RTC comments "2x msaa and unorm16 support virtually guaranteed as minimum OS target".
- **MSAA sample positions**: xenia-canary [`cc4981a465`](https://github.com/xenia-canary/xenia-canary/commit/cc4981a465) "[GPU] Rasterize at Xenos MSAA sample positions" (goldislead, 2026-08-31; ported by furqanagwan #313). Accuracy, not speed.
- **Tessellation**: xenia-canary [`3eab2b8b39`](https://github.com/xenia-canary/xenia-canary/commit/3eab2b8b39) "[GPU] Handle tessellated triangle strip and fan draws" (2026-08-08; rexglue #506). Xenia's Vulkan tessellation uses real hull/domain shaders; MoltenVK implements those as a compute pre-pass + a new render command encoder per tessellated draw (historical issue [#567](https://github.com/KhronosGroup/MoltenVK/issues/567) describes exactly that mechanism), which is what we replaced for continuous quad patches. XeniOS/Metal Shader Converter route the same hull shaders through Apple's geometry/tessellation emulation instead; andrew17182 found adaptive vs uniform tessellation made no measurable difference, and the expensive part was the memexport-only factor-computing draws.
- **Geometry-shader-free point sprites / rect lists**: xenia issue [#1213](https://github.com/xenia-project/xenia/issues/1213) (open since 2018): Triang3l's plan is to merge the GS logic into the vertex shader using a built-in strip index pattern ("0,1,2,3,restart,4,5,6,7,restart...") because a compute pre-pass "will result in lots of render pass breaking, and, with tiling, potentially tile loads and stores". MoltenVK has no geometry shaders ([#1524](https://github.com/KhronosGroup/MoltenVK/issues/1524), open) and 1.4.0 added "MSL: option to provide a default point size"; 1.4.1 fixed default `gl_PointSize` in tessellation shaders.
- **Memexport**: xenia-canary [#1093](https://github.com/xenia-canary/xenia-canary/issues/1093) (memexport stream fails when the guest physical heap is near-full; open); the Vulkan command processor's `memexport_readback_buffer_` path is what the SDK's `readback_memexport` derives from. The Fable-specific knowledge (fur shells and terrain tessellation factors are memexported; readback via the physical view after CB completion with no GPU wait) is in andrew17182's commits `254e3d5f` / `ef356688`.
- Xenia upstream has no MoltenVK/Metal support and no open MSAA-on-TBDR work; `xenia-project/xenia#596` "Xenia for Mac?" (92 comments) is the only thread.

## 4. MoltenVK: issues, releases, knobs

Releases (`gh api repos/KhronosGroup/MoltenVK/releases`): **1.4.0** (2025-08-20) memoryless images no longer added to residency sets, fix pipeline pixel format vs dynamic rendering attachments, MSL default point size option, `atomic_thread_fence` for MSL 3.2; **1.4.1** (2025-11-30) "New descriptor state tracker implementation to improve performance", occlusion queries across multiple render passes and accumulated in parallel, fix default `gl_PointSize` in tessellation shaders; **1.4.2** (2026-07-24) `MVKRenderPass: encode barriers for subpass dependencies`, `VK_EXT_sampler_filter_minmax`, `gl_DrawID`, fix device loss with imported `MTLTexture` + argument buffers; **1.4.3** = `701747d6` (upstream `development` pin) plus the swapchain 1x1 fix `4d74f17e` (abradburne #487). 1.3.0 (2025-05) added `VK_KHR/EXT_load_store_op_none` and "Implement barriers using Metal fences".

Issues that matter:
- [#1740](https://github.com/KhronosGroup/MoltenVK/issues/1740) `VK_EXT_multisampled_render_to_single_sampled` feature request (open since 2022, 0 comments) — the extension that would let MSAA live only in tile memory with the resolve on store; not available.
- [#490](https://github.com/KhronosGroup/MoltenVK/issues/490) subpasses with transient (lazily allocated / memoryless) attachments not working correctly (open); [#1308](https://github.com/KhronosGroup/MoltenVK/issues/1308) memoryless attachments cannot have load/store actions; [#1374](https://github.com/KhronosGroup/MoltenVK/issues/1374) framebuffer fetch (open) — i.e. the Metal-native ways to keep the 4x MSAA colour/depth in tile memory are not reachable through MoltenVK's render-pass model today; every render pass end stores the multisampled attachments to memory and the next load reloads them. This is why render-pass count, not draw count, dominates our MSAA cost and why bigmah's two fixes are so effective.
- [#1244](https://github.com/KhronosGroup/MoltenVK/issues/1244) TBDR per-pixel render-target size limits; [#2471](https://github.com/KhronosGroup/MoltenVK/issues/2471) triangle fans / uint8 index buffers break the render pass (CPU-side index conversion inserts a blit); [#567](https://github.com/KhronosGroup/MoltenVK/issues/567) tessellation restarts the render encoder (mechanism unchanged).
- [#1597](https://github.com/KhronosGroup/MoltenVK/issues/1597) "MoltenVK shouldn't check every resource on a barrier" (open; CrossOver disables the checks) and [#1749](https://github.com/KhronosGroup/MoltenVK/issues/1749) submit/encode CPU cost (indirect-count loops); [#2841](https://github.com/KhronosGroup/MoltenVK/issues/2841) (2026-09-25) a ~60 ms fixed GPU cost per frame independent of resolution in a Vulkan game — a symptom profile similar to ours, still open.
- [#2765](https://github.com/KhronosGroup/MoltenVK/issues/2765), [#1656](https://github.com/KhronosGroup/MoltenVK/issues/1656), [#1311](https://github.com/KhronosGroup/MoltenVK/issues/1311): sample-rate shading defects on Apple GPUs (argues against the FSI path).
- Configuration knobs present in the 1.4.1 dylib we ship (`strings libMoltenVK.dylib`): `MVK_CONFIG_PREFILL_METAL_COMMAND_BUFFERS` (0 = encode everything at submit, fastest; 1/2 = encode at `vkEndCommandBuffer`), `MVK_CONFIG_SYNCHRONOUS_QUEUE_SUBMITS` (default 1; 0 dispatches submission to a GCD queue), `MVK_CONFIG_USE_METAL_ARGUMENT_BUFFERS` (default 1), `MVK_CONFIG_USE_MTLHEAP` (0/1/2), `MVK_CONFIG_SHOULD_MAXIMIZE_CONCURRENT_COMPILATION` (default 0; macOS 13.3+), `MVK_CONFIG_FAST_MATH_ENABLED` (default 2), `MVK_CONFIG_USE_COMMAND_POOLING`, `MVK_CONFIG_PERFORMANCE_TRACKING` + `MVK_CONFIG_ACTIVITY_PERFORMANCE_LOGGING_STYLE` (per-activity timing without code changes).
